# ADR-0074: ربط Git: الـ OAuth للتجهيز بس، والـ deploy keys للوصول

- **الحالة:** مقبول. قرار Sabry يوم 2026-10-30، وبيعدّل الجزء الخاص بتوكن GitLab في [`M4-Pipelines.md`](../M4-Pipelines.md) (قسم GitLab والسؤال 8).
- **التاريخ:** 2026-10-30
- **بيكمّل:** [ADR-0012](0012-git-providers.md) و[ADR-0072](0072-webhooks-and-git-credentials.md).

## السياق
- الخطة كانت بتقول إن GitLab بيتوصّل بتوكن API (personal أو project أو group) بيتخزّن متشفّر على السيرفر ويفضل معاه، وبيستخدمه في كل حاجة: ربط المشروع، وقراية التعريف، والتأكد من الـ sha، والـ commit statuses.
- التوكن ده واسع: توكن personal بـ scope `api` بيوصل لكل مستودعات الشخص، ولو اتسرّب من السيرفر الضرر كبير. ولو صاحبه ساب الشركة الربط بيقع.

## القرار
- **الـ OAuth للتجهيز بس، والـ deploy keys للوصول.** أي صلاحية واسعة بتتستخدم وقت الربط وبس، والوصول الدايم بمفتاح محصور في مستودع واحد وللقراية بس.
- **GitHub (M4.5):** الـ GitHub App زي الخطة، بتوكنات installation قصيرة (ساعة) محصورة في المستودع. مفيش تغيير.
- **GitLab (M4.6):**
  - flow «اربط GitLab» بـ OAuth2. المستخدم بيختار المشروع، وداو بيعمل بالـ API deploy key للمشروع ده (للقراية بس) والـ webhook بتوكن لكل مستودع.
  - **توكن المستخدم الواسع مابيتخزّنش:** بيتستخدم في نداءات التجهيز بس وبيترمي بعدها على طول. يعني `"GitConnections"."TokenSealed"` مش هيشيل توكن OAuth لمستخدم.
  - **صاحب النسخة بيسجّل تطبيق GitLab OAuth مرة واحدة** من «إعدادات السيرفر» (ADR-0063): الـ client id والـ secret (للكتابة بس)، ولكل `BaseUrl` (GitLab.com أو self-managed) تطبيق.
  - الـ flow نفسه في `"GitSetupFlows"` بـ `"Kind" = 'gitlab_oauth'` (اتضاف في `00043`): الـ `state` مربوط بالجلسة، والـ hash بس في قاعدة البيانات، و10 دقايق، زي الـ OIDC.
- **Git عام (M4.4):** deploy key بيتولّد في السيرفر وwebhook موقّع، والواجهة بتعرض الخطوات للنسخ واللصق في M4.10. ده اللي اتنفّذ في ADR-0072.

## اللي لازم M4.6 يحسمه (بيتسأل Sabry وقتها)
من غير توكن دايم، فيه 3 حاجات في الخطة كانت معتمدة على API GitLab بعد الربط:
1. **قراية `.dhow.yml`** (القرار 2): ممكن تمشي بالـ discovery job زي Git عام، لأن الـ deploy key كفاية للـ checkout.
2. **التأكد إن الـ sha رأس الـ ref** (القرار 11): ممكن يمشي من الـ checkout زي Git عام (الـ sha لازم في تاريخ الـ ref). ده أضعف شوية من التأكد بالـ API، لأن الـ webhook بتاع GitLab بتوكن مش بتوقيع على الـ body.
3. **الـ commit statuses** (القرار 14): محتاجة كتابة بالـ API. البدائل: project access token بـ scope ضيق بيتعمل وقت الربط (متاح على self-managed كله، وعلى GitLab.com في Premium بس، زي السؤال 8)، أو مفيش statuses على GitLab والإشعارات (M7) بتغطيها زي Git عام.
- **التوصية المبدئية:** (1) و(2) زي Git عام، و(3) project access token لو متاح، وغير كده من غير statuses مع رسالة واضحة في الواجهة.

## العواقب
- تسريب قاعدة البيانات أو `DHOW_SECRET_KEY` بيكشف مفاتيح للقراية بس، كل واحد على مستودع واحد، مش توكن على حساب شخص.
- GitLab بقى أقرب لـ Git عام في المسار (checkout بالـ deploy key وhost key متثبّت)، فالكود المشترك أكتر.
- محتاجين إعداد جديد في «إعدادات السيرفر» لتطبيقات GitLab OAuth، مع M4.6.
