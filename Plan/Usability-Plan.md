# خطة السهولة: ملاحظات Sabry بعد أول تشغيل على Windows (2026-10-28)

Sabry شغّل داو لأول مرة على Windows عن طريق WSL، ووصل للداشبورد بعد مشاكل كتير. الملاحظات اللي طلعت 5، والخطة دي بتحوّل كل واحدة لشغل محدد. كل مهمة مكتوبة بحيث تتنفّذ لوحدها.

## قرارات Sabry
- **الترتيب:** الطلبات والموارد الأول، وبعدهم Docker Compose، وبعده اللغة، وبعدها الإعدادات، وفي الآخر شكل الداشبورد.
- **اللغة:** عربية مبسطة في الواجهة ورسائل السيرفر والـ CLI بس. `Plan/` والكلام مع Sabry يفضلوا بالمصري.
- **`DHOW_PUBLIC_URL`:** يفضل في env.
- **الداشبورد:**
  - المشاكل اللي شايفها: باهتة وفاضية، والتنقل ملخبط، والمحتوى مش مفيد، والخطوط والمسافات مش مريحة.
  - فيه أماكن فاضية كتير، والـ Tabs بتختفي في `?stack=organization` لما يختار آخر تاب.
  - المطلوب مراجعة UI/UX كاملة، وتكملة الصفحات الناقصة، والشغل يمشي بالتوازي.

## اللي اتعمل خلاص
**[#33](https://github.com/Khaymah/dhow/pull/33) (اندمج):** السكربت بيتجاهل الـ PATH بتاع Windows جوه WSL.

**[#34](https://github.com/Khaymah/dhow/pull/34) (اندمج):**
- `setup.ps1` بيحدّث الـ clone الموجود.
- `libatomic` بتتسطّب.
- التعرّف على WSL بقى أقوى.
- شريط تقدّم للتحميل.
- فحص كل رد مع إعادة السؤال لو غلط.
- السكربت شغّال على bash 3.2 بتاع macOS.
- أوامر واضحة في الآخر لتشغيل `make` جوه WSL.
- اختبار في الـ CI بيشغّل السكربت كامل على 4 توزيعات نضيفة، فيها PATH شبه Windows.

## 1. التسطيب للمبتدئين

**المشكلة:**
- التطوير محتاج Go وNode وpnpm وPostgres وmake على الجهاز نفسه.
- على Windows لازم WSL كمان.
- كل أداة منهم نقطة ممكن تقع.

**الحل المقترح:** بيئة تطوير بـ Docker Compose بس (`deploy/dev/compose.yaml`).
- المطلوب: Docker Desktop وgit، ومفيش حاجة تانية.
- أمر واحد: `docker compose -f deploy/dev/compose.yaml up`. بيقوّم Postgres 18، وسيرفر Go بـ live reload، وVite.
- `.env.dev` بيتولّد أوتوماتيك أول مرة، من container صغير بيكتب الأسرار العشوائية.
- على Windows بيشتغل من PowerShell مباشرة من غير WSL يدوي، لأن Docker Desktop نفسه بيستخدم WSL من جوه.
- `setup.sh` و`setup.ps1` يفضلوا للي عايز يشتغل native.

**المهام:**
1. `deploy/dev/compose.yaml`:
   - خدمة `db` (Postgres 18، volume، healthcheck).
   - خدمة `server` (image فيها Go، الكود متركّب كـ volume، و`go run`).
   - خدمة `web` (Node + pnpm و`vite --host`).
   - خدمة `init` بتولّد `.env.dev` لو مش موجود.
2. **Cache:** modules بتاعة Go والـ store بتاع pnpm في volumes، عشان أول تشغيل بس اللي يبقى بطيء.
3. **الوثائق:** `docs/development.md` يبدأ بالطريقة دي («أسهل طريقة»)، وبعدها الطريقة native.
4. **CI:** job بيقوّم الـ compose ويستنى `/api/v1/health/ready`، ويتأكد إن `setup_url` ظهر في اللوج.

**المخاطر:**
- مراقبة الملفات (live reload) على volumes من Windows ممكن تبقى بطيئة. هنستخدم polling في Vite وفي إعادة تشغيل Go.

## 2. الداشبورد: الشكل وعدد الطلبات

**المشكلة اللي اتأكدت منها:**
- كل الـ hooks تقريبًا بـ `staleTime: 0`، منها `useOrganization` و`useSessions` و`useMfa`.
- فكل component بيتعمله mount بيعيد الطلب. وفتح `?stack=account` لوحده بيعمل 6 طلبات.
- `/me` والمنظمة والـ MFA بيتطلبوا أكتر من مرة في نفس الصفحة.

**المهام:**
1. **قياس الأول:** اختبار Playwright بيفتح كل صفحة وكل slide، ويعدّ الطلبات لكل مسار، ويكتبهم في جدول. ده يبقى خط الأساس.
2. **`QueryClient`:**
   - `staleTime` افتراضي معقول (30 ثانية مثلًا) مع `refetchOnWindowFocus` للبيانات اللي بتتغير بس.
   - نشيل `staleTime: 0` من الـ hooks.
   - التحديث بعد أي تعديل يبقى بـ `invalidateQueries` المحدد.
3. **بيانات الجلسة:**
   - `/me` والمنظمة الحالية يتجابوا مرة واحدة وقت الـ boot، ويتحطوا في الـ cache.
   - الـ slides تقرا من الـ cache ومتطلبش تاني.
4. **ميزانية طلبات في الـ CI:** نفس اختبار Playwright يفشل لو أي صفحة عدّت عدد طلبات محدد، أو لو نفس المسار اتطلب مرتين.
5. **الشكل:**
   - مراجعة UX كاملة الأول (agent `ui-ux`) على الصفحات الحالية.
   - بعدها اقتراح مكتوب بصور قبل أي كود.
   - Sabry يقول إيه اللي مش عاجبه بالظبط، والاتجاه يتسجّل في ADR جديد بدل ADR-0034 لو اتغيّر.

## 3. اللغة العربية

**المشكلة:**
- النصوص دلوقتي «مصري مهذّب»، وده مكتوب في `CLAUDE.md` و`Plan/Glossary.md`.
- Sabry عايزها **عربية مبسطة**: مش عامية ومش فصحى تقيلة. جمل قصيرة، وكلمات مفهومة لأي عربي.

**المهام:**
1. **قرار:** ADR جديد بيحدد الأسلوب:
   - أمثلة قبل وبعد.
   - كلمات ممنوعة: عامية زي «مقدرناش» و«حمّل الصفحة تاني»، وفصحى تقيلة زي «يتعذّر».
   - شكل رسائل الأخطاء والأزرار.
2. **التحديث:** `Plan/Glossary.md`، وسطر الأسلوب في `CLAUDE.md`.
3. **مراجعة النصوص:**
   - كل النصوص في `apps/web/Src/I18n/Locales/**/Ar.ts`.
   - رسائل الأخطاء في السيرفر (`Core/I18n`).
   - رسائل `dhow` CLI والـ installer.
4. **Hook أو اختبار:** يرفض كلمات العامية المعروفة في ملفات `Ar`، عشان ماترجعش تاني.

## 4. نقل الإعدادات من env لقاعدة البيانات

**الوضع:** السيرفر بيقرا حوالي 30 متغير `DHOW_*`.

**المقترح:**

| يفضل في env (لازم قبل الاتصال بالداتابيز أو سر) | يتنقل للداتابيز ويتعدّل من لوحة الأدمن |
|---|---|
| `DHOW_DATABASE_URL` / `_FILE` | SMTP كله (host وport وTLS وuser وpassword وfrom) |
| `DHOW_SECRET_KEY` / `_FILE` (بيتولّد أوتوماتيك) | `DHOW_OIDC_PROVIDERS` |
| `DHOW_LISTEN_ADDR` و`DHOW_RUNNER_LISTEN_ADDR` | `DHOW_ORG_CREATION` |
| `DHOW_RUNNER_TLS_CERT_FILE` / `KEY_FILE` | حدود الطلبات (`RATE_LIMIT_*`) |
| `DHOW_TRUSTED_PROXIES` (أمان الشبكة قبل أي طلب) | `DHOW_LOG_RETENTION_DAYS` و`JOB_LOG_MAX_BYTES` و`SSE_MAX_STREAMS` و`RUNNER_MAX_POLLS` و`LOG_READ_CONNS` |
| `DHOW_DEV` و`DHOW_LOG_LEVEL` | `DHOW_BREACHED_PASSWORD_CHECK` |
| | `DHOW_PUBLIC_URL`: بيتسجّل وقت أول setup ويتعدّل من اللوحة (محتاج قرار) |

**المبادئ:**
- **الأسرار:** كلمة سر SMTP وأسرار OIDC بتتشفّر في الداتابيز بالـ `SECRET_KEY` (نفس آلية الأسرار الموجودة). مابترجعش في أي response، وتتكتب بس.
- **Fail closed:** قيمة غلط في الداتابيز ماتوقعش السيرفر. اللوحة بتتحقق منها قبل الحفظ، ولو قيمة قديمة بقت غلط السيرفر بيستخدم الافتراضي الآمن ويسجّل تحذير.
- **الصلاحيات:** التعديل لصاحب الـ instance بس، من خلال `can()`. وكل تغيير بيتسجّل في الـ audit log.
- **الترحيل:** لو المتغير موجود في env وقت الإقلاع وجدول الإعدادات فاضي، قيمته بتتنسخ مرة واحدة للداتابيز مع تحذير إن المتغير بقى ملوش لازمة. بعد إصدار واحد، المتغير بيترفض.
- **التطبيق من غير restart:** الخدمات بتقرا الإعدادات من cache بيتحدّث عن طريق `Core/EventBus` لما الأدمن يحفظ.

**المهام:**
1. ADR جديد بالتقسيم ده والمبادئ.
2. Migration: جدول `"InstanceSettings"` (key/value مكتوب بأنواع، والأسرار متشفّرة) بالأعمدة الأربعة الأساسية.
3. موديول `Settings`:
   - Service فيه cache.
   - Endpoints في `openapi.yaml`.
   - صفوف في جدول اختبار الـ routes.
   - اختبار بيثبت إن الأسرار مش بترجع في أي response.
4. نقل SMTP الأول، وبعده OIDC، وبعده الباقي، وكل خطوة في PR لوحدها.
5. صفحة «إعدادات النظام» في الواجهة لصاحب الـ instance.
6. `setup.sh` يبطّل يسأل عن SMTP خالص.

## 5. متطلبات التشغيل المعلنة

**المشكلة:**
- مفيش رقم معلن لأقل وأكتر موارد.
- ممكن حد يسطّب على جهاز 1 GB ram، والسيرفر يقع من غير ما يعرف السبب.

**المهام:**
1. **القياس:** `deploy/bench/` بيقوّم السيرفر وPostgres وrunner في Compose بحدود ذاكرة ثابتة. بيقيس الـ RSS والـ CPU والمساحة لـ 3 أحمال:
   - فاضي.
   - 10 مستخدمين و5 jobs متوازية.
   - 50 مستخدم و20 job متوازية.
   ويشغّل نفس الـ suite عند 512 MB و1 GB و2 GB لحد ما يوصل لأقل حد بيشتغل.
2. **الوثائق:** صفحة `docs/requirements.md` فيها جدول **الحد الأدنى** و**الموصى به** و**للأحمال الكبيرة**. كل جدول منهم للسيرفر مع Postgres، وللـ runner لوحده (الـ runner بيحتاج زيادة لكل job على حسب `Resources`).
3. **الأدوات:**
   - `dhow doctor` والـ installer بيرفضوا يكمّلوا تحت الحد الأدنى (fail closed)، مع رسالة بتقول الرقم المطلوب.
   - وبيحذّروا تحت الموصى به.
4. **CI:** job ليلي بيعيد القياس ويفشل لو الاستهلاك زاد عن الرقم المعلن بأكتر من 20%.
